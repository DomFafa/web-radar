## Closed P1 — Switching actors onto the same project retains the previous actor's unsaved editor

- Location: `src/client/App.tsx:66` and `src/client/App.tsx:163` (`accept` and the `Editor` key; line numbers at review time).
- Trigger: An embedded editor has local unsaved content, and a later valid authentication result changes user/workspace while selecting the same project. This is possible for a project owner and its workspace administrator, who are both authorized to open the project.
- Problem: `accept` queues `setSelected(null)` and then `setSelected(result.projectId)` in the same callback. React batches them, so the effective project ID stays unchanged. `Editor` is keyed only by that ID and is retained. Clearing `lastPrincipal` does not unmount it because the new `principal` is already available.
- Impact: The next actor sees the earlier actor's unsaved text, local conflict choices and operation state; it can subsequently be saved under the new actor. This contradicts the documented different-identity clearing behavior. It does not demonstrate a server-side project permission bypass.
- Reproduction: Run `node /tmp/wr-frontend-review.mjs` with the explicit local test server on port 8788 and port 5173 free. The harness creates its own project, obtains real local owner/admin sessions, hosts a local allowed-origin parent, and supplies those sessions through intercepted handoff exchange responses. After owner authentication, type `OWNER UNSAVED PRIVATE DRAFT` into the company field. Send an admin authentication result targeting the same project.
- Observed: Two exchange responses were handled, but the field remained `OWNER UNSAVED PRIVATE DRAFT` with `有未保存修改`. The saved server value was `SAVED REVIEW COMPANY`.
- Expected: A changed actor opens a fresh editor from authorized server data. Same-actor token renewal must continue preserving local unsaved input.
- Recommendation: Include stable user/workspace identity in the editor lifetime/key, or explicitly reset all actor-scoped editor state on actor changes. Do not use the rotating session token as the identity, since that would discard work during same-account renewal.
- Validation: Add a component/browser regression for owner → admin on the same project, plus same-owner renewal and cross-workspace switching.
- Cost: S. Original acceptance blocker: **yes** (identity isolation); now closed.

## Closed P1 — Command responses silently overwrite edits entered while the request is pending

- Location: `src/client/Editor.tsx:236`–`243` (`command`), with `install` at `:108` and the still-enabled script input at `:1148`.
- Trigger: After a clean save, start a command such as script confirmation and type more text before its response returns.
- Problem: The pre-request dirty check protects only edits made during `save()`. Once `post()` starts, ordinary inputs and editor navigation remain enabled. The eventual `install(result.project)` unconditionally replaces the current local project and clears its dirty state without checking whether it changed while the request was pending.
- Impact: New user input disappears and the editor displays a saved/confirmed version. The same helper is used by script/storyboard confirmation, accepting a video, source import/application and taking the site offline. This is silent local data loss, despite the existing protection around saves and background refreshes.
- Reproduction: The same harness starts a real `POST /api/projects/:id/confirm-script`, captures its successful 200 response and delays delivery to the browser. While pending, fill the script input with `NEW TEXT TYPED WHILE CONFIRMING`, then release the response.
- Observed: The pending input was accepted; after response delivery it reverted to `Saved review script` and the save indicator became `已保存 · V3`. No browser page errors occurred.
- Expected: Either editing is consistently unavailable throughout the command, or new local edits survive the response and remain explicitly unsaved, with confirmation invalidated where appropriate.
- Recommendation: Apply command responses with the same snapshot/change discipline as saves. If the user edited meanwhile, retain the local input and reconcile the returned server version through the existing conflict flow rather than blindly installing it. An input lock must cover every editable surface if that simpler approach is chosen.
- Validation: Hold a command response, edit an existing field, release it, and assert the edit remains unsaved or was unavailable to edit; also confirm the normal clean command result installs correctly.
- Cost: S–M. Original acceptance blocker: **yes** (data loss); now closed.
