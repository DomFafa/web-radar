# 仓库同步与线上发布约定

2026-10-18 更新长期协作约定；Cloudflare 常规发布规则沿用 2026-10-01 的确认内容。

## 仓库与合并

1. 长期协作仓库为 [DomFafa/web-radar](https://github.com/DomFafa/web-radar)，日常集成主线为 `codex/web-radar-v1`，与仓库默认分支及 `.github/release-source.json` 保持一致。
2. 每项任务从最新主线新建自己的功能分支，例如 `codex/larrybin-contact-search`。协作者在各自的功能分支提交；需要共同维护同一分支时先明确分工。
3. 功能分支推送到 `DomFafa/web-radar`，Pull Request 的目标统一为 `codex/web-radar-v1`。同一任务已有未合并 PR 时更新该 PR。
4. 合并前完成代码审查和当前提交的 CI 检查：`local`、`browser`、`template-browser`、`render-quality`、`web-radar-integration`。遵守分支保护；改变 PR 目标或提交后重新确认检查对应的源码和合并基线。
5. 负责人审核后通过 PR 合并。代理可准备提交、维护 PR 和验证结果；执行合并须获得负责人当次明确授权。合并后的主线作为后续任务的起点。
6. 历史任务分支保留追溯用途；尚有独立改动的分支另行评审。统一主线时保留已有撤销，不把旧实验改动自动混入。

每次开始任务先核对实际仓库、远端 URL、分支和工作区状态；本地 remote 名称可能不同，推送目标以 URL 为准。主线合并与线上发布分别记录，部署仍按下述规则执行并验证。

## Cloudflare 发布

用户要求更新线上时，使用项目配置的 `CLOUDFLARE_ACCOUNT_ID` 与 `CLOUDFLARE_API_TOKEN` 直接发布 Web Radar Worker 和静态资源。上游 PR 合并及 `production-release` 工作流不是此常规发布路径的前置条件，无需再次请求“流程例外”。这项约定取代此前将上述前置条件用于所有生产发布的说明。

发布仍需完成与改动相应的验证：

1. 核对推送的完整提交号、发布目标及构建内容；保留类型检查、相关测试、模板浏览器和 API 合同验证。
2. 发布前检查生产绑定和变量，保留现有数据库、存储、队列、浏览器和服务配置；凭据仅从私有环境读取，不写入 Git、公开产物或日志。
3. 使用仓库锁定版本的 Wrangler 发布，保留生产变量（`--keep-vars`），记录完整源提交号、Worker 版本与部署 ID。
4. 发布后验证健康状态及实际受影响的页面、模板目录、API 文档和静态资源。只有验证通过才报告上线完成。

已有 [production-release 工作流说明](controlled-production-release.md) 作为可选的上游 Actions 发布方式保留；选择该工作流时仍遵守其自身检查，不伪造分支、检查结果或工作流环境。

应用左下角的「最近更新」固定为该版本的前端构建时间，按北京时间显示；「更新人」取该版本最近一次 Git 源码提交的作者，不随页面刷新或当前登录账号变化。Vite 构建时读取本地 Git 元信息并写入静态资源，无需页面额外请求；保留产物及构建时间，恢复原产物时保留原版本信息。

服务器副本继续按用户要求单独部署与验证。只更新文档时不重复部署应用；向上游提交 PR 不会代替任一环境的线上发布。
