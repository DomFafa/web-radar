# Product Radar 产品资料到统一网站：模板规划与验收方法

本轮范围为 Auravell、Careflow、Toorun、Lumi、Mello。五套使用同一组三款已保存产品设计做横向验收。Pawfect 是用户认可的质量参照，不是给所有模板套用的页面样式。

## 1. 先固定事实，再规划网站

Product Radar 负责产品事实、确认主图、原套图、来源、规格状态和生成任务。Web Radar 负责模板位置、文字容量、构图、页面布局及实际渲染。两边以版本化材料合同对接。

每款产品始终保留 ID、确认主图及来源。材质、尺寸、功能、建议规格分别按原始事实状态传递。`Proposed` 不能变成已量产，`Approx.` 不能变成精确测量，来源冲突的空值不能由模型补写。原套图可以帮助理解产品，不能被默认为每个网站场景的最终图。

站点受众来自真实公司资料卡的 customerTypes、网站 brief 和产品用途。不能固定把所有站点写成面向批发商、零售商的 B 端网站；受众未提供时使用中性产品介绍，有明确 B 端或家庭消费者定位时按该定位写作。Product Radar 的整站规划、场景生成和替换提示词应使用同一规则。

公司信息来自真实资料卡。没有公司史、工厂、团队、认证、销量或评价时，不生成这些“证据”。About us 可以介绍真实产品和设计，而不编一个公司故事。缺少报价和库存时使用询盘，不把原模板价目表改成假产品价格。

## 2. 把原模板拆成内容任务

先辨认模板的视觉特点，再逐块写出阅读目的。每块必须能回答：

1. 访问者在这里了解什么，下一步去哪里？
2. 这一块引用哪款产品、哪些已知事实？
3. 是原主图、独立场景、真实公司资料，还是无需图片？
4. 桌面和手机各占多少空间，主体在哪、如何裁切？
5. 文案用什么格式，最多多少字符和行数？

课程、医生、咖啡菜单、招聘、套餐等原行业内容逐项重判。无有效产品用途的区块删除，不通过改几个名词保留。图标使用 CSS/SVG，不把邮箱图标、地图、头像等旧资源一律列为生图任务。

## 3. 一站一个视觉计划，一图一个明确用途

`website.visual-plan.v1` 先结合产品主图、事实与合同位置形成整站计划。计划规定环境、光线、色彩、摄影尺度、产品分配、各段信息顺序。模板色彩控制背景和排版，不修改产品本身颜色。

所有新场景使用 `image.generate-new.v1` 和 `reusePolicy: generate-new`。生成请求必须携带绑定产品 ID、确认主图、形态/材质/比例约束和该位置的具体构图。不同图片位置不合并为同一个生成任务，不拿一张图轮流填 hero、about、contact。

原主图用于目录卡片和详情身份确认，保持原图、完整 `contain` 显示。这种准确复用有明确用途。桌面/手机的同一个逻辑图片可以使用同一源图和合适裁切；另一内容角色需要另一张场景。场景图用于表达情境，不证明性能、工厂、认证或其他事实。

完整套装的数量要对整张画面计数：盒内、桌面和手里是互不重叠的分配，不能各自再画一套；局部特写可以展示合理子集。已有品牌字样、包装图案和标志属于产品身份，禁止新增广告叠字不能被解释为删除原品牌。生成后仍需逐图核对，按实际错误定点修改并保留前后回执，不能把状态 ready 视为产品保真已通过。

## 4. 文字与原生布局一起设计

合同使用可理解的位置名，如 `hero-headline`、`product-context`、`about-detail`，不让资料生产者面对原站成百上千个匿名 DOM 文本节点。每个位置写明用途、容量、事实规则和产品绑定。

模型提交纯文本，字体、斜体、按钮、段落、响应式和排版由模板控制。不能把正文直接塞进标题，不用强制省略号截断确认规格。原生模板必须实际消费每个必需图片/文字位置；没有渲染消费者的位置不能成为必填生产要求。相关区块的图、文字、原图卡片和跳转须指向同一绑定产品，不能一处用规划选中的产品、另一处默认用产品数组第一项。

产品较多时，首页使用有上限的精选和场景选择，目录与详情仍覆盖全部产品。单款、三款、七款分别检查，不能只让三款示例碰巧好看。

| Toorun | 云朵、四色、四个异形图框、五格拼贴、彩色卡片 | 开场产品印象；真实设计观察；产品情境拼贴；目录；浏览比较询盘；About | 四幅首屏和五格情境分别规定画面任务，独立生成；无意义联系装饰不生成 |

精确位置、尺寸、容量和构图以 `src/templates/themes/{auravell,careflow,toorun,lumi,mello}/product-materials.ts` 为准；对应 `product-renderer.ts` 是其渲染消费者。

## 6. 接口与版本

本轮继续使用 `wr-template-materials-v1`，保留现有产品、资料、确认、提交、接收和项目预览接口，不新增数据库语义或身份流程。Product Radar 已支持显式传入 `templateRevision`。

候选版本：`guideRevision: 2026-10-02.2`，`contractRevision: 2026-10-02.<templateId>-materials.2`。候选通过显式版本读取；默认目录仍返回已有 `.1`，旧项目保持原合同和渲染路径。用户验收前不自动迁移已有网站。

合同被另一库读取后会按版本缓存。上线后的内容修订必须新建版本，不能原版本悄悄换含义。新增模板能力与用户最终视觉验收分开记录。

## 7. 真实验收流程

固定三款产品设计：水果 12 件套、LOOF 空气净化器、紫色羊毛绒。原素材共 17 张，保存来源、SHA、事实和规格冲突。它们是已保存的产品设计与套图，不代表已验证实物照片。

每套都走线上 Product Radar 创建资料 → 整站规划 → 真实场景生成 → ready → 逐图/文案检查 → 确认 → 提交 → Web Radar accepted → 实际项目预览。不能用手改 HTML、手替换图片或本地 mock 结果代替这条流程。

程序检查覆盖合同完整性、独立场景、原主图身份、全部位置消费、1/3/7 产品、五页路由、历史版本隔离、询盘和私有预览边界。浏览器检查覆盖桌面/手机、所有产品详情、长文案、图像裁切、导航、场景切换和表单。动效须保持初始稳定、只执行一次、支持减少动态效果。

最终记录每套材料 ID、项目 ID、生成耗时、实际图数、模型/用量回执、问题与重做理由、可浏览预览。成功提交或健康检查都不等于视觉合格；最终风格效果交由用户验收。
