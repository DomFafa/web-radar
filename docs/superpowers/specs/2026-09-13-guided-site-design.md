# Guided static site design

Approved flow: retain the current Web Radar UI shell; upload products and company facts → image-aware LLM asks one useful question at a time with exactly four model-generated choices and a fifth fixed choice “都不是，我要自定义” that expands a custom input → customer approves the consolidated brief and page list → Image 2.5 homepage → approve homepage → remaining images referencing homepage plus original products and brief → approve set → screenshot-to-code → browser preview and publication.

Scope: five base page types (home, catalog, detail, about, contact), plus up to three justified extra informational pages recommended by the LLM and explicitly included in brief confirmation. Extra IDs are `extra-<safe-slug>` and routes `/LANG/extra-SLUG/`; all products share the detail design. No video, ecommerce, new authentication, billing, database migration or production infrastructure work.

The text provider must receive actual uploaded images and image-role metadata, existing facts and answer history. It returns a single question or a structured brief with approved language copy, product translations and page content. Missing factual claims cannot be invented. Questions seek intended use, audience, conversion goal, brand/visual direction, layout/content hierarchy, preserved details and exclusions following the official image prompting guide. Skip facts already known; at most 10 answered questions, then finish from available facts and explicitly omit unknown claims. Invalid upstream output is a recoverable error, never a fabricated success.

The server owns consultation state, question IDs, answer history and approvals. Generic draft updates cannot forge them. Input edits invalidate consultation and all dependent designs. Brief edits request a new LLM proposal and invalidate approvals. Pending revisionContext retains the previous brief and requested change across follow-up questions; a ready result clears it. Changes to applied copy or product translations also revoke approval without discarding intake history. Exactly one live consultation job per project; request-id deduplication and revision/job ownership prevent stale results attaching. Existing confirmed legacy static artifacts can still preview/publish; new page-image jobs require an approved brief. Normal quota/auth behavior stays intact.

A ready brief contains: summary, audience, goal, visualDirection, layout, brandColor, keep[], avoid[], pages[], copy by selected language and translations by product ID/language. Each page contains id, label (Chinese operator label), purpose, content by selected language with title and sections[{heading,body}]. Base pages retain current deterministic product/factual/title bindings and also bind their approved page sections; extra pages use page.title and section.N.heading/body bindings. Every supplied section must appear exactly once in approved order, with corresponding section counts across selected languages. The detail page uses generic shared sections and per-product facts for product-specific descriptions. Do not invent manufacturing, certification, sales or contact claims.

Image prompt explicitly labels reference roles, preserves actual product geometry/branding and includes approved brief, page goal and exact text. Homepage approval is a hard gate; all planned page images are required for set approval/build. Changing homepage clears dependent images. Builder accepts exactly the planned images, creates every planned route per language, and uses actual product files, safe navigation and functional inquiry bindings. No vendor library modifications.

Acceptance: targeted state/provider/schema tests; Python extra-page assembly/request validation tests; full existing typecheck/tests/build; local fixture browser through question/brief/home/extra-page/build stages and stale edits. Real-provider output quality and production deployment must be reported separately from fixture acceptance. No new full paid image/site generation is required to prove state plumbing.
