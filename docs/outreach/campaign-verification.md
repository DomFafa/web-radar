# 邮件发送结果核实

核实流程与发送结果独立：待核实 → 核实中 → 已核实。已核实只表示本轮查询已完成，不代表所有邮件发送成功；没有可信回执的邮件单独显示“结果未确认”，不增加已受理或已送达计数。

## 手动核实

在发送记录的任务详情中点击「立即核实」。后台任务分页读取原 Resend 帐号，按冻结的发件人、收件人和 `wr_recipient_id` 标识确认邮件；已有服务商 ID 时直接读取该邮件。关闭页面不会终止核实，重新打开可查看查询进度、确认数和剩余数。

- 仅有相同邮箱不足以匹配。完整查询后无标识或多个匹配时，任务显示“已核实”，并保留结果未确认的数量和发送保护。
- 权限不足、网络失败或达到查询上限显示“核实未完成”；10 分钟无进展或运行超过 30 分钟显示中断/超时，可点击“重试核实”。不会把未完成的查询标为已核实。
- 查询不会发送邮件、重新入队收件人、清除发送尝试或恢复暂停任务。
- 每次队列执行最多连续处理 8 页/8 秒，逐页保存进度，减少反复排队。与发送任务共享服务商请求额度，限流后延迟继续。
- 当前远端查证支持 Resend。缺少冻结快照或使用其它服务商时明确提示人工核实。
- 新收到的可信 Resend 回调也会更新任务；全部不确定结果消除且无待发邮件后，自动退出待核实。

旧队列仅在不确定发送后延迟恢复尝试（通常约 3 分钟），没有无限周期核查。无可信证据时不会经过某个固定时间自动判成功。

## 统计口径

本项目已受理按收件人/服务商邮件 ID 去重。Resend Metrics 是帐号级聚合指标，可包含其它域名、其它应用和历史任务；不能将 Metrics 的 sent 直接写入某一活动的 total_sent。

当前本项目送达、打开、点击计数是累计证据：打开与点击分别依据各自事件，后续退信不会抹去曾有的互动时间。比例以已受理数为分母。Resend 的打开/点击率以 delivered 为分母，delivery_rate 以 sent 为分母。时间范围、指标定义、异步事件和缓存都会造成差异。对账应先匹配相同帐号和邮件 ID，再比较原始事件。

## 发布

已有 `0018_campaign_review.sql` 的部署无需新迁移。列表、详情和核实 API 返回同一份持久化核实记录；刷新或重新登录保留已核实状态。首次接入时先应用该迁移，再发布 API、队列和前端。Cloudflare 与服务器使用相同核实逻辑；保持服务器原生存储、队列适配不变。迁移不修改原有发送记录。
