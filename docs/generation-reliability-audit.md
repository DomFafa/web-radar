# 网站生成可靠性根因核查

2026-09-14。用户已明确选择保留“图片模型先出设计稿，再转网站”。本轮优先修复第一页图片输入容量；Hero 产品合集拆成独立背景素材是后续图生站优化方向。本文区分已完成的输入编译修复与尚未完成的网站构建可靠性改造。部署状态见本轮 acceptance。

## 当前证据

- 真实 API 重新读取确认：水杯项目在首页成功后，用户自行提交的四张内页图全部 succeeded，一次尝试，整组从提交到全部完成约 228 秒。恢复后的首页真实运行约 45 秒。原失败创建到恢复的 29 分钟包含工程排查和人工恢复，不能当作单次模型推理耗时。
- 另一个已完成的八产品站点构建为 249 秒。其后约一小时的设计调优属于人工返工；现有本地验收记录明确包含跨多次运行选取页面、人工裁切和 CSS 修正，不是完整无人干预生成。
- 本轮 API 快照、任务状态及时间在 `artifacts/generation-reliability-20260914/`，仅存于 Git 忽略的私有目录。没有替客户确认设计、触发生成或发布。

## 根因

1. **允许的输入与下游容量不一致。** `src/worker/domain.ts` 的来源条件允许任意 JSON；`domain-service.ts` 允许 4,000 字符的修改要求。当前首页提示词已为 30,514 字符，因此一个合法修改仍可让它确定超出 32,000。完整条件占约 70%，其中包含原始产品创作指令。位置索引只能节省重复字符，无法容纳任意长的合法输入。检查发生在任务进入队列后，重试仍使用相同冻结输入。
2. **图片和网页由两次独立生成决定。** 图片模型把照片、文字和装饰合成一张图；网页转换再推断裁切、组件、样式和响应布局。现有代码已经有可信事实绑定和几何检查，但文字残片、主体断边与视觉还原并没有完整可判定的最终检查。截图复刻不是输入图片生成成功就能保证的结果。
3. **构建进度没有成为恢复检查点。** `app.py` 保存整单输入和最终文件；`builder.py` 逐页构建，已有中间证据落盘，却没有按输入摘要读取并复用通过验收的页面。后页失败会丢失整单可用结果，服务重启将 running 直接标为失败。
4. **时间与队列预算缺少统一约束。** 本地最新实现单页含规划、可选素材复核、两次 Agent、两次渲染；每次 Agent 最多 30 个内部回合，五页串行。整单又限制 20 分钟，单个阶段的最大允许时长不能同时兑现。Worker 全局调度和 Python 单消费者还会累加不同客户的排队时间。
5. **自动测试与真实交付验收有缺口。** 203 项 Worker 测试和 198 项 Python 测试证明已有流程约束；它们不能证明每个新样本都不需要人工修图。部分链接、所有详情页及表单模拟检查仍属于外部人工启动的验收脚本。

上述 Python 机制来自当前仓库代码和上一轮本地验收。新视觉修复尚未部署到独立 Python 服务，本轮没有通过 SSH 重新审计其部署源码；不要将本地最新质量检查能力视为已经在线。

## 已选择：图片模型先出设计稿

保留图片模型出首页设计稿、客户确认风格、生成内页、转换网站的顺序。原始资料完整存档；页面可见的已确认原文单独保留，非可见产品事实仍按原产品 ID 带入设计上下文。

图片请求应用上限为 28,000 个 UTF-16 字符，首版预留完整 4,000 字符修改空间，因此首版输入最多 24,000。完整序列化后再核对容量，包含 JSON 转义、全部规则、参考图标签和修改要求。页面文案本身放不下时，在创建任务、清理旧图和预留额度之前拒绝。

先对完全重复的原文片段建立共享字典，用固定编号引用，所有空格、换行、否定条件和产品归属可逐字反解，不调用模型。无损编译仍不能容纳时，只将必要的最长非可见资料交给文字服务整理并独立复核；具体漏项自动修正一次，再次复核不过则不提交图片请求。文字整理不是无损编码，不能把模型复核视为绝对语义保证。

真实失败样本的首页编译从 30,162 降为 23,471 字符，加完整修改预留为 27,471。8 个原产品 ID、40 个条件归属及条件原文反解一致，已确认首页和公共页脚文案不变；0 次文字调用，准备约 4 ms。早期直接让模型概括的真实测试曾遗漏要求，已保留失败证据，未向图片服务发送未经复核的摘要。

## 后续图片稿转网页工作

保留现有图片模型出设计稿的顺序。需要把原始资料与有容量上限的页面设计输入分开：原始条件完整保存，先提取并核对网站实际需要的产品约束；出图前检查各页面正文、参考图数量及修改空间。不能静默删掉要求以通过长度检查。长内容须在方案确认前解决，已确认资料不得擅改。

同时增加每页输入摘要、已验收素材和页面检查点；恢复时只继续未完成的确定步骤。已提交但结果不明的付费调用不得盲目重放。先生成公共首页，再按明确资源预算处理内页；最终复查实际裁切图片、全部输出路由、图片、产品对应关系、桌面/手机和模拟表单。此路径保留更自由的图片设计，但裁图与响应式还原仍有推断成本。

## 两条路径共同的交付门槛

- 客户按现有页面按钮即可完成，过程没有工程师修改输入、图片坐标或 HTML。
- 长文案、多个产品、不同产品比例和第二语言都有真实样本，报告首轮通过率及 p50/p95 耗时；未完成真实样本前不承诺耗时和成功率。
- 排队、生成、校验、失败原因和可恢复状态明确；刷新和关闭页面不会创建重复任务。
- 限制错误在付费执行前识别；可恢复的网络/查询失败继续原任务，确定性的输入/权限错误不会反复重试。
- 故障注入验证服务重启、后页失败、资源下载中断和重复点击；通过的页面不重复生成，不自动重复不确定的付费请求。
- 验证部署版本、已登录客户流程、真实生成产物和账号范围，分别保存证据。没有以单元测试通过替代生产全链路验收。

产品路径已经确定。首版输入容量修复不能代表裁图、HTML 还原和整单任务恢复已完成；这些仍需独立实施和真实无人干预验收。
